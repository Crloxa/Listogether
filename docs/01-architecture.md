# 架构与同步模型

## 总体结构

```text
房主浏览器 ──┐                         ┌── 成员浏览器
             ├─ WebSocket 控制/信令 ────┤
             └─ WebRTC 音频流 ──────────┘
                         │
                    Relay 服务
       (房间状态、鉴权、信令、健康检查；不保存音频)
```

本地应用通过出站连接访问 Relay，避免要求用户配置端口转发。互联网 WebRTC 连接需要 STUN；无法直连时使用受控 TURN 中继。Relay 只转发必要的信令和状态，音频是否经过 TURN 由 WebRTC 协商结果决定。

## 控制面与媒体面

### 控制面

控制面负责房间成员、权限、队列、播放事件、准备状态和重连快照。房主是播放控制权威，Relay 负责鉴权、广播和版本校验。

最小房间状态包括：`roomId`、`revision`、`currentTrack`、`positionMs`、`playing`、`transitionId`、`startAt`、`queue`、`members` 和每个成员的 `ready/status`。

### 媒体面

房主从本地文件解码音频，通过 Web Audio 或等效方式送入 WebRTC 音频轨道。每个成员有独立的 PeerConnection。房主不应把本地路径发给成员，成员只接收媒体流和公开元数据。

迟到成员无法从已经结束的实时 WebRTC 轨道倒放，因此成员主动点击重新同步时，房主需要用可定位的本地音频源，为该成员从目标时间戳创建新的音频流。

## 播放准备屏障

1. 房主切换下一首时发出带 `transitionId`、目标歌曲、起始位置和未来 `startAt` 的 `PREPARE`。
2. 成员建立或重建媒体流，缓冲新歌曲并定位到统一起始位置，完成后发送 `READY`。
3. 房主只等待当前在线成员；心跳超时的成员标记为离线，不永久阻塞屏障。
4. 全部有效成员 ready 后，房主确认 `START`；客户端在 `startAt` 播放。
5. 播放过程中不高频广播进度。暂停、拖动、切歌、重连、手动同步和明显漂移才产生校正事件。

## 迟到和重新同步

- 迟到成员加入当前歌曲时不自动跳转、不强制改变当前播放；界面提示“当前歌曲已开始”，提供房间内“重新同步”按钮。
- 成员点击“重新同步”时，只请求自己的 `SNAPSHOT` 和媒体流重建，不修改房间状态，也不触发全房间暂停。
- 房主拖动当前歌曲进度时只广播新的权威状态，不启动全员准备屏障；需要修复的成员自行点击重新同步。
- 全房间播放下一首时，所有当前在线成员必须经过准备屏障并在统一 `startAt` 播放。掉线成员由心跳标记为离线，不永久阻塞其他人。

## 消息原则

事件必须包含事件类型、房间版本、发送者角色、唯一事件 ID 和必要的时间戳。服务端拒绝过期版本、未知成员或越权操作。重连优先获取完整快照，再处理快照之后的事件。

## 安全边界

- 邀请 token 使用高熵随机值，可过期、撤销、限人数并可选密码。
- 所有房间输入、链接和显示文本都需校验和转义；链接解析要防 SSRF，不允许访问任意内网地址。
- OAuth 使用 PKCE 和最小 scope；token 不进入房间状态、URL、前端日志或截图。
- Relay 采用 TLS、连接限流、心跳超时和消息大小限制。
- 本地文件默认不保存到 Relay；临时流连接关闭后应释放相关资源。
